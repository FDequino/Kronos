# Design

<!-- impeccable:design-schema 1 -->

## World

Financial terminal, Operate mode. Dark charcoal surfaces by default (now with a properly-designed light counterpart, see Theming), one committed accent (cool blue) reserved for primary actions/selection/focus, gain/loss carried entirely by dedicated green/red semantics (never the accent). Two-family type system: a sans for all UI chrome, a monospace with tabular figures for every number. No emoji, no icon fonts — nav icons are hand-authored inline SVG, one consistent 1.5px stroke.

## Tokens

Defined in `webui/static/css/tokens.css`.

- Surfaces: `--bg-sidebar` (#0b0d11, darkest), `--bg-content` (#12151c), `--bg-elevated` (#1a1e27, panels/tables), `--bg-elevated-hover`.
- Borders: `--border` (hairline, 1px everywhere), `--border-strong` (inputs).
- Text: `--text-primary`, `--text-secondary`, `--text-tertiary` (#828b9c — kept light enough to clear 4.5:1 on `--bg-elevated`; do not darken without rechecking contrast).
- Accent: `--accent` / `--accent-dim` / `--accent-strong` — primary actions, active nav, focus rings only. Never used for gain/loss.
- Semantic: `--positive` / `--negative` / `--warning`, each with a `-dim` background variant for tags and banners.
- Type: `--font-sans` (IBM Plex Sans, via Google Fonts), `--font-mono` (IBM Plex Mono, tabular-nums). Scale `--step--1` through `--step-4`, fixed rem, ~1.125–1.2 ratio. Floor is 12px (0.75rem) for any label/caption text — nothing smaller ships.
- Radius: `--radius` (6px, panels), `--radius-sm` (4px, inputs/buttons).

## Components

CSS lives split by concern under `webui/static/css/` (`base.css`, `layout.css`, `components/*.css`) — one file per component family, no monolith. Loaded via plain `<link>` tags from `base.html`; no bundler.

- **Sidebar** (`components/sidebar.css`): fixed 240px, dark, active item = accent-dim background + 1px accent left border + accent icon color. Collapses to a horizontal scrollable bar under 860px for the nav row itself; below that same breakpoint the bottom nav (see Responsive/mobile below) takes over section-to-section navigation, so the collapsed sidebar row is mostly a Buscar/Notificaciones/Preferencias utility strip on phone widths, not the primary way to switch sections anymore.
- **Panel** (`components/panel.css`): the one container primitive — border + bg-elevated + radius. `.panel-header` for title/action row, `.panel-body` for padded content, `.panel-body.flush` (padding 0, `overflow-x: auto`) when the only child is a table. Every `.panel`'s direct child is `.panel-header`/`.panel-body`/`.panel-body.flush` — never bare content — so inset is structural, not incidental.
- **Stat strip** (`components/panel.css`): flex row of label+value pairs with hairline dividers, inside a `.panel-body.flush`. Replaces "icon+heading+text" stat cards.
- **Table** (`components/table.css`): dense, hairline row dividers, numeric columns right-aligned in mono via `.num`/`td.num`. `.table-empty` for the zero-rows state (always a sentence, never "no data"). See Shared table infrastructure and Responsive/mobile below for the chrome (search/filter/group/column-manager) and the card layout every one of the app's 7 tables now shares.
- **Forms/buttons/status/loading/slider**: one file each, same token set. Disabled state = 0.45 opacity (accepted low contrast on disabled controls per WCAG's exemption for inactive components).
- **User menu** (`components/user-menu.css`, `shared/user-menu.js`): theme toggle, an ARS⇄USD currency toggle, and a chevron that expands the four BNA rate variants (divisa/billete × compra/venta) as radios, default divisa venta. Now anchored in the header (`top: 100%; right: 0`, see Top bar below) rather than the sidebar foot — the bottom-left anchor/mobile-downward-flip it used to need no longer exists because a header-anchored popover only ever opens downward regardless of viewport.
- **Risk gauge** (`components/risk-gauge.css`, `charts/risk-gauge.js`): one horizontal bar (0–100, bajo/medio/alto semantic coloring) reused for both the portfolio-level score on Resumen and the per-instrument score on the detail page — same component, two call sites, never a bespoke one-off. The fill is a full-width element scaled via `transform: scaleX()` with `transform-origin: left`, not an animated `width`, to keep the transition off layout-affecting properties.
- **Allocation donut** (`components/allocation-chart.css`, `charts/allocation-donut.js`): hand-built SVG arc donut (no charting library) grouping holdings by instrument type, with a color-coded legend showing each type's % of total value. Each type gets its own distinct hue (blue/amber/green/magenta/cyan/gray) — an earlier palette shaded two types in nearly the same blue, which read as "no se entiende" (indistinguishable) rather than merely suboptimal. Both the arc and its legend row are clickable (`onSelectType` callback) and apply the exact same type filter as the Tenencias chips below — the donut isn't a static illustration, it's another way to drive the one filter state. Each arc also carries a native SVG `<title>` for a zero-JS hover tooltip (label, value, %).
- **Table groups + type filter** (`components/table.css`, `portfolio/holdings.js`): Tenencias is **one** `<table>` with **one** `<thead>` — repeating a full header row per instrument type (one early version did this) reads as a pile of disconnected mini-tables, which is exactly the "tablas cruzadas" complaint that shipped this fix. Each group instead opens with a lightweight `<tr class="table-group-row" data-group="bono">` spanning all columns; every data row below it carries the same `data-group`. A row of type-filter chips ("Todos" + one per type present, built from the live holdings, never hardcoded) toggles a `type-filter-hidden` class on non-matching rows; `shared/table-filter.js`'s text search toggles its own, separate `table-row-hidden` class. Both classes independently `display: none` — a row is visible only when *neither* is present, so the two filters never fight over shared state, and `table-filter.js`'s `refreshGroupRows()` re-checks a group-row's own visibility (hidden once every row under it is hidden by either filter) after either one runs.
- **Info tooltip** (`components/info-tooltip.css`, `shared/info-tooltip.js`): a small "i" trigger that opens a click-toggled popover (same elevation language as the user menu: `bg-elevated` + border + shadow) showing the plain-language explanation a metric already has *plus* its formula substituted with the real numbers for that instance — never just the final number. One shared `initInfoTooltips()` wires every `.info-tooltip-trigger` via a single delegated document click listener, so it keeps working on rows rendered after the fact (new holdings, re-renders) with zero re-wiring. Currently used for every risk score (portfolio gauge, per-row Tenencias tag, detail page Riesgo tab) via `charts/risk-gauge.js`'s `instrumentRiskFormulaLines`/`portfolioRiskFormulaLines`, which read the intermediate numbers `portfolio/risk.py` already computes (`weight`, `volatility_score`) but didn't expose until this was built.

## Two charting libraries, each doing only what it's good at

`lightweight-charts` (TradingView's engine) owns anything that is genuinely a financial time series — candles, the forecast chart, the accuracy chart, portfolio value over time. **ApexCharts** (added via CDN, same pattern) owns every other chart — pie, radial gauge, diverging bar — after hand-rolled SVG versions of all three were tried first and rejected: no real legend, no real tooltip (the browser's native SVG `<title>`, unstyled and slow to appear), slices with no visible separation, and P&L bars that all anchored to the left regardless of sign so gains and losses looked the same shape. A charting library gives legend/tooltip/axis for free and correctly; reinventing them in raw SVG was the actual root cause of "se ve pedorro," not a detail to polish later. `charts/apex-theme.js` is the one place the dark/light palette and base chart options are defined, read by every Apex-based module (`allocation-donut.js`, `risk-gauge.js`, `pnl-bar-chart.js`, `risk-distribution-chart.js`) so none of them hardcode a second copy of the token colors.

**Chart instance lifecycle**: every Apex-based render function stores its instance on `container._chart` (not a module-level `let currentChart`) and destroys it there before re-rendering. A module-level variable silently breaks the moment the same render function is called for two different containers in the same page (it happened here: `pnl-bar-chart.js` renders both the absolute and the % charts — the second call was destroying the first's instance before it ever painted). Container-scoped storage is the only version of this that's actually correct.

The P&L bar chart is a **true diverging bar** (ApexCharts' horizontal bar naturally diverges from zero when the series has mixed signs) — gains extend right in green, losses extend left in red from a shared zero axis. An earlier version anchored every bar to the left regardless of sign, which made a -9% loss and a +9% gain look like the same shape in a different color — color alone doesn't communicate direction as fast as position does.

## Sidebar: collapsible

`shared/sidebar-collapse.js` toggles a `.collapsed` class on `#sidebar` (width `240px` → `64px`, nav labels/brand text/foot meta hidden via `display: none`, state in `localStorage`). The toggle button lives in its own full-width strip between the brand and the nav — not inside `.sidebar-brand` itself — specifically so collapsing doesn't need brand-row-specific layout logic; the button's position never moves. Hidden entirely under 860px, where the sidebar is already a horizontal bar, not a column worth collapsing. First icon tried for the toggle combined a chevron with a vertical bar meant to read as "a bracket" — at 15px it read as a stray capital "K" instead; the fix was simply using *only* the chevron.

## Why the BYMA universe fetch no longer starves other requests

`GET /explorer/search` (a real call to `data912.com` for the ~1300-symbol BYMA universe) used to fire unconditionally on every `/portfolio` load regardless of which tab was open. The day data912 had a transient 502, that one fetch (15s timeout) didn't just fail its own tab — it visibly starved the *other*, unrelated Resumen requests (holdings, risk, history) of the browser's small per-origin connection pool, so Resumen rendered as a wall of empty panels despite every one of those endpoints being individually healthy. `GET /explorer/search` now also catches its own failures and returns `{"error": ...}, 502` instead of leaking a Werkzeug debug-mode HTML traceback to an API consumer expecting JSON.

Explorador no longer exists as its own tab (see Navigation below), so the original fix — gating the fetch behind `location.hash === '#explorador'` — no longer applies, and the lazy-load pattern it relied on didn't carry over: every view's data now loads on every `/portfolio` page load regardless of which hash is active (`portfolio/main.js`'s `DOMContentLoaded` handler calls every `initXxxView()`/`loadXxx()` unconditionally, not just the active one). `portfolio/instrumentos.js`'s `loadAll()` fetches the BYMA universe (`api.explorerSearch('')`, same `limit=2000`) as part of that same eager load. What keeps this from reproducing the original starvation bug is sequencing, not gating: `main.js` awaits `loadInstrumentos()` (which includes the universe fetch) in its own `Promise.all` *before* kicking off the second `Promise.all` that holds Resumen's requests (holdings, history, plazos fijos, etc.) — the two batches run one after the other, not all at once, so the universe fetch no longer competes with Resumen's requests for the same connection-pool slots. This is a different mechanism than the hash-gated laziness this section used to describe, carrying the same intent (don't let one page's heaviest request starve another's) through main.js's load order instead.

## Top bar: search, preferences, notifications

The sidebar used to end in a "Preferencias" text button that opened upward from the bottom of a 240px-tall column — once that same panel needed to work from the *top* of the page instead (moved to the header, per direct feedback referencing another app's account menu), it also stopped needing the upward-anchor/mobile-downward-override hack entirely, since a header-anchored popover only ever has room to open downward regardless of viewport size.

- **User menu** (`shared/user-menu.js`, `.user-menu-panel` anchored `top: 100%; right: 0`): currency is a `.segmented-toggle` (ARS **and** USD both always visible, the active one highlighted) — not a single button that cycles between two text states, which read as "which one am I looking at" rather than "which one is active." Theme is a real `.switch` (checkbox styled as a toggle) for the same reason. The BNA rate variant picker (4 radios behind a chevron) is unchanged, just reparented.
- **Notifications** (`shared/notifications.js`, bell icon + badge count + `.notifications-panel`): this is the same data `portfolio/alerts.js` always computed (vencimientos, dividendos cobrados, señales de venta) — `alerts.js` now only exports `computeAlerts()` (pure data, fetches holdings itself so it has no required caller args) and the rendering/open-close/badge-count logic lives in `notifications.js`, globally wired in `base.html` so it's reachable from any page, not just Resumen. Moving it out of Resumen's page flow was also what that view needed to stop feeling like a stack of unrelated panels.
- **Search**: centered in a new `.page-header-center` flex zone between the title and the action icons, widened (`max-width: 560px`) from the old corner-anchored small input. `.page-header` is three flex zones (`title | center | actions`), not a two-way `justify-content: space-between` — the center zone needs its own flex slot to actually center rather than just "whatever's left of the title." The global command palette (see Routing and global search below) is a separate trigger from this per-view search box, reachable from the same header.

## KPIs expand in place, never navigate away

"Hacer click y entrar en el dato" was first (wrongly) built as click-to-scroll to a different section — the actual ask was an accordion: the stat card itself grows downward to reveal its own breakdown, never taking the viewport anywhere else. Each `.stat` in the stat-strip has a sibling `.stat-detail` (`hidden` by default, toggled on click of the card): Valor Total's detail is the per-type breakdown, P&L's is a ganando/perdiendo top-3, Posiciones' is a count by type. Valor Total additionally always shows its Tenencias/Cauciones split as a permanently-visible `.stat-sub` line (not worth hiding — two numbers, always relevant) plus, once there's a reconstructed history to diff against, a day-over-day delta arrow. A fourth KPI, Cotización USD (current BNA rate for the selected variant), answers "no estás poniendo ni $ ni USD en ningún lado" directly, as does the new `shared/format.js:fmtMoney()` — every money figure in Tenencias, the stat-strip, and the detail position tab now carries an explicit `$`/`USD` prefix instead of a bare, ambiguous number.

## Historial real reconstruido (no solo desde hoy)

`portfolio/history.py:reconstruct_portfolio_value()` answers "how did my real net worth actually move" using data that was already sitting in the database and never used this way: `transactions` (what you held on any given day, by cumulative sum) × `price_history` (the real close on that day, carry-forward over gaps) = a **real** value series going back to your first transaction, not just from whenever this feature shipped. A **teórico** series runs the same calculation but substitutes Kronos's predicted close wherever `forecasts.result_json.predicted` actually covers that date, falling back to the real price everywhere else — "what would this be worth if Kronos's calls had been the ones that happened," never extrapolated beyond where a forecast genuinely exists.

Two honesty constraints that shaped the implementation:
- Most held instruments had **zero** rows in `price_history` (it only back-fills when a forecast runs against that instrument) — reconstructing against an empty series would have silently under-counted most of the portfolio. `_ensure_history()` lazily backfills any held, data912-sourced accion/cedear/bono the first time this endpoint runs (one-time network cost per instrument, cached after). Some symbols (short-term LETRAS, ON, manually-priced funds) have no historical endpoint at all — those are listed in the response's `missing_symbols` and shown verbatim under the chart, rather than being silently absent from a total that looks complete but isn't.
- `price_history` and forecast `predicted` values are already normalized "per 1 unit" at the `fetchers.py` boundary (see Multi-currency section) — this module does **not** re-divide bono/on prices by 100. It did, once, during development, and produced a total 100x too small — the exact bug this normalization boundary exists to prevent, reintroduced by a second piece of code forgetting the convention.
- No historical BNA rate is tracked day-by-day, so USD-denominated instruments in the reconstruction are converted at **today's** rate across the whole series, not the rate that applied on each past day — a declared, accepted simplification, not a precision the data can't actually back up.

## Tenencias: tabla plana, no grupos fusionados

A grouped structure (one `<tr class="table-group-row">` spanning all columns per instrument type) was tried first to add visual classification — it was the direct cause of "no se entiende, no coinciden las columnas": a merged full-width row breaks the eye's sense that every column lines up continuously, making one table read as several disconnected ones glued together. Tenencias is now one flat table with **Tipo as an ordinary, sortable column** (same `shared/sortable-table.js` used elsewhere), backed by the shared search/filter/group chrome described in Shared table infrastructure below. Real vertical borders between every column plus zebra-striped rows (`table.css`) complete the "como un Excel" ask; the filter chips above the table still narrow by type, they just no longer double as the thing providing visual grouping.

## Theming

Dark is the only hand-authored palette in `tokens.css`; `theme-light.css` overrides every color token under `:root[data-theme="light"]` with its own values (off-white surfaces, near-black text, deeper-saturated accent/semantic colors re-picked for contrast on white — never a CSS `invert()` or lightness flip). An inline script in `base.html`'s `<head>` applies the saved `data-theme` from `localStorage` before first paint (no flash of the wrong theme); `shared/theme.js` wires the sidebar toggle and persists the choice. `base.css` adds a 180ms background/border/color transition to body, panels, sidebar, forecast cards, and form controls — the one motion this surface earns, tied to a real state change, not decorative.

## Forecast card + candlestick chart

`portfolio/forecast-card.js` (the collapsed symbol + signal-badge + "Ver detalle" unit, tag-colored comprar/mantener/vender) was built for the standalone Señales dashboard grid and the Explorador search result, both of which have since been absorbed into Decisiones and Instrumentos respectively (see Routing below) with their own row/card markup — no current view imports `createForecastCard` anymore. The file and its CSS (`components/forecast-card.css`) still ship, loaded from `base.html`, as dead code from before the merge; not removed in this pass, not canonized as a pattern for new work either. The chart/explanation rendering it used to own inline lives on in `instrument-detail.js`, which is the one place that code is actually exercised today.

Charting is **lightweight-charts** (TradingView's own open-source engine, pinned implicitly to whatever `latest` resolves to — currently v5, which uses `chart.addSeries(SeriesType, options)`, not the v4 `addCandlestickSeries()`/`addLineSeries()` shorthands) rather than the Plotly already used on the original Kronos predictor page — real candles, SMA/EMA overlay, a secondary RSI pane, in the same dark/light palette as the rest of the app. Series other than the candles themselves (predicted close, SMA, EMA) set `lastValueVisible: false` / `priceLineVisible: false` — they inform through color/dash-style only, so their price-line labels don't stack on top of each other. One hard-learned rule: never call `createChart`/`addSeries` while the chart's container is still `display: none` — the container's `clientWidth` reads 0 and the chart silently renders nothing; flip visibility on *before* constructing the chart, not after.

`charts/candlestick-chart.js` also owns three small pieces that make the chart legible on its own, without a caption explaining it (`components/chart-overlay.css`):
- **Legend** (`chartLegendHtml()`): a static row of swatch+label pairs (Real/SMA 20/EMA 20/Predicho) reusing the exact colors already in `PALETTE` — never a second color definition to keep in sync.
- **Tooltip**: `chart.subscribeCrosshairMove()` drives a single absolutely-positioned div inside the chart container. It never reads values back off the series (`param.seriesData`) — instead it builds a `time -> index` lookup once from `forecast.historical`/`forecast.predicted` and indexes straight into the same arrays (`indicators.sma_20`, `ema_20`, `rsi_14`) the series were built from. That's what lets one tooltip show OHLC *and* SMA/EMA *and* RSI together even though RSI lives in a visually separate pane rendered by a second, unrelated `createChart` call.
- **Range shortcuts** (`rangeControlsHtml()` + `wireRangeControls()`): 1M/3M/6M/1A/Todo buttons that call `chart.timeScale().setVisibleRange(...)` against data already in memory — never a new fetch. Every preset anchors its right edge to the *last predicted point*, not "today," so the forecast cone is always in view; only how far back history starts changes.

## Drill-down navigation

Resumen, Instrumentos, Decisiones, and Transacciones all go "from less to more": a collapsed row/card shows just a symbol, a type, and a signal, and every one of them links to `#detalle/<symbol>` for the full picture — one dedicated full-width page within the workspace, never an expansion inside a grid cell (a 3-up grid expanding one cell used to push its neighbors around). `portfolio/tabs.js` recognizes the `detalle/` hash prefix as a dynamic route distinct from the fixed view list and hands off to `portfolio/instrument-detail.js`, which renders into `#instrument-detail-root`. Its one "Volver" action is a plain `<a href="#resumen">` **breadcrumb above the panel** (`.detail-breadcrumb`), not a lone button sitting by itself inside its own `.panel-header` strip — a bare button in an otherwise-empty toolbar read as "en un lugar rarísimo" once it was the only thing on the page with nothing to anchor it. A real `<a>` also means middle-click/keyboard/right-click-to-copy all work for free, which a `click` handler on a `<button>` didn't give.

The detail page itself has a **local tab bar** (`components/detail-tabs.css`) — Pronóstico / Posición / Riesgo / Precisión — instead of stacking all of it in one long column (an earlier version did exactly that and read as "una aglomeración de información" once Posición and Riesgo were added alongside the chart). Posición and Riesgo only appear as tabs when the symbol is an actual holding with that data; Precisión appears whenever the symbol has a local `instrument_id` (held or not — any instrument added via Instrumentos accumulates its own forecast history). A symbol opened from Instrumentos' discovery rows (BYMA universe, not yet added to the portfolio) with no local row at all gets just the one Pronóstico tab, and the bar itself doesn't render when there's nothing to switch between (`tabsBarHtml()` returns `''` for a single-tab list). Tab state is local DOM state (an `active` class + `hidden` attribute), never a second hash segment — `#detalle/GGAL/riesgo` would be over-engineering for a UI concern that never needs to be linkable on its own.

One gotcha the Precisión tab re-triggered: its chart must **not** be constructed eagerly alongside Pronóstico/Posición/Riesgo, because it isn't the default-active tab — its container is still `hidden` (same effect as `display: none`) at render time, so `createChart` would read a 0 width and draw nothing (the exact failure mode already called out below for the Pronóstico chart, just reached through a different hidden mechanism). Fix: `loadAccuracy()` only runs the first time the Precisión tab button is clicked, not on initial page render.

## Instrumentos: catalog and market browser merged into one table

What shipped first as two separate tabs — "Catálogo" (CRUD over instruments you've actually added) and "Explorador BYMA" (live search over the full ~1300-symbol market, lists everything by default rather than gating on a typed query, which is what a world-class screener like TradingView or Yahoo Finance does) — read as two partial views of overlapping data with different interactions, and are now one table: a symbol already in your catalog shows once, as a catalog row enriched with the live price/%-change the old Explorador tab carried; a symbol that's in the BYMA universe but not yet added shows as a discovery row with an "Agregar a cartera" action instead of Editar/Eliminar. A row of bucket filters (Todos / En Cartera / CEDEARs / Acciones / Bonos, `.segmented-toggle`, horizontally scrollable so 5 options don't overflow at 375px) replaces the old separate tabs. This view owns the legacy redirects (`#explorador`, `#comparar` → `#instrumentos`, see Routing below) for anyone with an old link.

It's a real `<table>` (sortable columns via `shared/sortable-table.js`, `.table-link` rows into the same `#detalle/<symbol>` drill-down as everywhere else), backed by the shared search-bar/column-manager/table-chrome infrastructure described below. Rendering ~1300 unfiltered rows as one page would make the whole document 50,000+ px tall (confirmed the hard way) — `.table-scroll` (`max-height: 70vh; overflow-y: auto`) caps it to one bounded, internally-scrolling panel with a sticky `thead` whenever nothing is grouped; grouped, each group starts collapsed instead (`lastRenderedGroupKey`), so the volume problem doesn't recur there. A "Mostrar más" page-size cutoff (`PAGE_SIZE = 100`) caps the ungrouped, unfiltered case the same way. Any other table that grows unbounded over time can reuse `.table-scroll`.

## Resumen: drill-down + genuinely informative (not just a snapshot)

Every number on Resumen used to be inert — a stat, a gauge, a table, with nothing behind it. Two complaints in the same breath ("dejame hacer click y entrar en cada dato" and, separately, "no me dice mucho") turned into one redesign, because they're two sides of the same problem: a dashboard that only shows the current totals, with no path to *why* and no path to *more*.

- **Stat-strip is clickable** (`portfolio/holdings.js`'s `wireStatClicks`): Valor Total always shows its Tenencias/Cauciones breakdown as a second line (no click needed — that one's cheap enough to just show), P&L click sorts Tenencias by P&L descending and scrolls to it, Posiciones click resets the type filter and scrolls. None of these needed a new endpoint — the data was already in hand, just not wired to anything.
- **Tenencias is sortable** (`shared/sortable-table.js`): sorting happens *within* each type group, never flattening the table — the grouping is structural, not decoration, so a sort has to respect it.
- **Riesgo de cartera shows its own breakdown directly**, not behind another click: "Mayores contribuyentes al riesgo" (top 3 by `valor_actual × risk.score`) sits right under the gauge's explanation.
- **Historial de cartera** (`portfolio_snapshots` table, written once per day inside `POST /refresh-quotes`, always in ARS regardless of the display-currency toggle so the line never jumps for the wrong reason): a real line chart of value over time. Brand-new portfolios show an honest "come back tomorrow" instead of a one-point chart pretending to be a trend.
- **Resumen narrativo** (`holdings.js`'s `buildNarrative`): one sentence synthesizing what's already fetched — today's biggest mover, the riskiest holding, and (only once 2+ snapshots exist) the value trend since the last one. Never invents a trend it can't measure yet.
- **Alertas** (`portfolio/alerts.js`): plazos fijos/cauciones vencidos o a vencer en ≤7 días, dividendos cobrados en los últimos 7 días, holdings con señal de venta — all assembled client-side from endpoints that already existed, zero new backend. An honest empty state ("Nada necesita tu atención ahora") when there's genuinely nothing, which is the common case for cauciones here since they're all historical/already-settled import data, not live open positions. Surfaced globally via the header's Notifications popover (see Top bar above), not only from Resumen's own page flow.
- **P&L por instrumento** (`charts/pnl-bar-chart.js`): a second chart next to the allocation donut — ranked horizontal bars, red/green, click-to-drill into the instrument. Answers "who's making or losing me money," which the donut ("where is my money") never could on its own.

## Multi-currency (ARS/USD)

Every instrument has a native `currency` (ARS or USD); the user picks a `display_currency` and a BNA rate variant in the user menu, and `/api/portfolio/holdings` converts every money field server-side using the live rate scraped from `bna.com.ar/Personas` (`portfolio/fetchers.py:fetch_bna_rates`, 5-minute in-memory cache — BNA has no public API). `pnl_pct` is never converted, since it's a ratio, not a monetary amount. Conversion lives in `routes.py`, not `db.py`, specifically to avoid a circular import (`db.py` is imported by `fetchers.py`, which is where the rate lookup lives). The inflation-adjustment toggle for ARS ("Ajustar ARS por inflación") lives in Ajustes > Moneda y Referencias now (see Decisiones/Ajustes: de-duplicating configuration below), synchronized through the same `currency-changed` event already used by the currency/USD-source/caución-rate controls — one event, every money-displaying view re-fetches on it, never a second notification channel for the same class of setting.

## Forecast accuracy (predicted vs. actual)

`portfolio/accuracy.py` answers "how good were Kronos's past calls, really" using data that already exists — every past `forecasts.result_json` (its `predicted` array) crossed against `price_history` once those same dates have a real, known close. No new table, no background job: it's a pure function over two already-queried row sets (`compute_accuracy(forecasts, price_history)`), exposed at `GET /instruments/<id>/accuracy`. Matching is by **date** (`YYYY-MM-DD`), not exact UNIX timestamp — `forecasts` stores predicted points as UTC seconds while `price_history` stores an ISO string, and the two are built through slightly different paths; comparing by calendar date sidesteps any timezone-of-day drift between them without losing precision that matters (nothing here is intraday). Directional accuracy counts only each forecast's *first* predicted step against its own last known historical close — the only comparison that is unambiguous regardless of how far out the rest of that run's horizon goes. If no past forecast has any predicted date old enough to already have a real price, the endpoint returns `null` and the UI shows an explicit "not enough time has passed yet" sentence — never a fabricated 0% or empty chart presented as a real answer.

## Routing and global search

`webui/nav.py`'s `NAV_ITEMS` is the only place sidebar/bottom-nav entries are listed (currently Resumen, Decisiones, Instrumentos, Transacciones, Plazos Fijos, Préstamos, Ajustes, plus Predictor as a separate route); `base.html` loops over it for both the sidebar and the bottom nav, `_icons.html` maps each `icon` key to its SVG. Adding a page means editing one Python list, not every template.

- **Two-level hash routing** (`portfolio/tabs.js`): `#vista` or `#vista/subtab` selects one of the fixed `VIEWS`; a `detalle/<symbol>` prefix is a distinct dynamic route handled separately (see Drill-down navigation above) and is deliberately excluded from both the fixed view list and the sidebar's active-link matching — there is intentionally no sidebar/bottom-nav item that's ever "active" while on a detail page. Each view carries its own `title`/`subtitle` pair (`VIEW_META`), replacing a single Jinja block that used to say "Mi Cartera" for all seven views regardless of which was open.
- **Legacy hash redirects** (`LEGACY_HASH_REDIRECTS` in `tabs.js`): the nav went from 10 items to 7 across two merges — Señales/Kronos/Propuestas into Decisiones, Explorador/Comparar into Instrumentos — and every old bookmarked hash (`#senales`, `#kronos`, `#propuestas`, `#bandeja`, `#explorador`, `#comparar`, plus `#core-satelite`/`#alertas` for views retired outright) still resolves to the right `[view, subtab]` pair instead of silently falling back to the default view. `webui/nav.py` documents the mapping for reference; the redirect itself only lives in `tabs.js` (not read from Python/Jinja).
- **Subtabs write their own URL segment** (`shared/subtabs.js`): a real click on a `.subtab-btn` does `history.pushState` to `#vista/subtab`, so it survives reload and works with back/forward. Activating a subtab programmatically (an incoming hash, a legacy redirect) dispatches a real `.click()` on the button — never a separate `activate()` call — specifically so any listener a view module hung directly off that button (lazy data loads) fires identically whether the user clicked or a redirect did. A `suppressHashWrite` flag stops that same programmatic click from re-pushing the hash that triggered it, avoiding a loop. Decisiones is a flat row of sibling subtabs (Oportunidades del Día / Configuración del Motor / Propuestas / Paper Trading / Rendimiento Histórico) — an earlier nested "subtabs inside a subtab" layout for Decisiones was removed as a "muñeca rusa" (Russian-doll) structure, so every subtab redirect target is a 2-segment hash, never a subtab nested inside another subtab.
- **Command palette** (`shared/command-palette.js`, Ctrl/Cmd+K, global across both `/portfolio` and `/`): a separate, app-wide jump-to-instrument search over the same `GET /explorer/search` BYMA-universe endpoint Instrumentos already uses — not scoped to whatever table is currently on screen, which is what the per-view search bar is for. Declines to open while a form modal is already open (`#modal-root` not hidden) rather than stacking over it. Debounced (150ms) with a monotonic request token so a stale response from an earlier keystroke can never clobber a newer one's results.

## Shared table infrastructure

What used to be bespoke per-table code (search, filter chips, grouping, column visibility, sorting) is now shared across all of the app's tables (Tenencias, Instrumentos, Transacciones, Rentas, Préstamos, Plazos Fijos, Cauciones) through two modules, so a new table reuses this chrome instead of reimplementing it:

- **`shared/search-bar.js`** (`createSearchBar`/`applySearchState`): one text input with live, no-Enter-required filtering (`fuzzyMatch`, accent/case-insensitive, edit-distance-≤1 typo tolerance as a fallback only after an exact substring match fails — never on multi-word fields, to keep the cost cheap against hundreds of rows per keystroke), an optional filter-chip panel, an optional "group by" radio list, and an optional named/saved-favorites column (`localStorage`-backed, scoped by a `favoritesKey` per table). `applySearchState` is the one function every table calls to turn `{query, activeFilters, groupKey}` into either a flat filtered row list or `{grouped, groups}`; `groupRowHtml`/`tableBodyRowsHtml`/`wireGroupToggles` render that result consistently, including an explicit empty-group message rather than a silently blank `tbody` when a filter leaves zero groups.
- **`shared/table-chrome.js`**: the column-visibility toggle (`columnToggleHtml`/`mountColumnToggle`), drag-to-reorder columns (`wireColumnDrag`), a sortable header-cell renderer tied into `shared/glossary.js` so a column label can carry its own hover definition, and the always-visible total row (`totalRowHtml`, computed off the currently-filtered rows, never the unfiltered dataset, so a total never silently disagrees with what's on screen). The column-toggle panel uses one delegated document-level click listener to close on outside-click regardless of how many tables with this chrome are on the same page — an earlier per-table version keyed off a single fixed ID and broke the moment two tables with this chrome coexisted.
- **Mobile card layout** is also table-chrome.js's responsibility; see Responsive/mobile below.

## Decisiones/Ajustes: de-duplicating configuration

Decisiones > Configuración del Motor used to carry a full duplicate editor (slider + TP/SL inputs + its own Guardar) for the same `capitalAllocation`/`satelliteExitParams` settings Ajustes already owned under "Motor Cuantitativo y Estrategia" — two places to change one value, and the Decisiones copy didn't even expose the Core threshold the Ajustes one did. Decisiones' Motor subtab is now a read-only summary with an "Editar en Ajustes" link; it still fetches `allocation`/`exitParams` itself, since Oportunidades del Día needs them for each card's "Monto sugerido," but editing happens in exactly one place. The same pass added the ARS inflation-adjustment toggle to Ajustes > Moneda y Referencias (it previously only existed in the old Preferencias popover) wired through the same `currency-changed` event as currency/USD-source/caución-rate, and renamed Ajustes' "Notificaciones" subtab to "Reporte PDF" — it was never anything but PDF-generation/Telegram-delivery settings, and the old name collided with the header bell, which is where real notifications (vencimientos, señales) now live (see Top bar above).

## Responsive/mobile

- **Bottom navigation under 860px** (`components/bottom-nav.css`, `shared/bottom-nav.js`): replaces the collapsed horizontal sidebar row as the primary way to move between sections on phone widths — the four most-used sections stay as direct, always-visible icons, plus a "Más" button that opens a bottom sheet (backdrop + Escape + outside-click to close, same dismissal pattern as every other popover in the app) for the rest of `NAV_ITEMS`. It reuses the existing `.nav-item`/`data-nav-id` markup, so `shared/nav.js`'s existing active-link matching marks the right bottom-nav item active without that file needing any bottom-nav-specific code. Fully hidden on desktop; the sidebar's own nav row (`.sidebar-nav a.nav-item[data-nav-id]`) is hidden in the same breakpoint since the bottom nav now owns that job — only the header's Buscar/Notificaciones/Preferencias utilities stay in the collapsed top strip.
- **Tables as expandable cards under 640px** (`table.css` + `table-chrome.js`'s `withMobileCardLayout`/`mobileExpandToggleHtml`/`wireMobileCardToggle`): every one of the app's 7 tables wraps its already-built `<td>` cells with this helper rather than each reimplementing a card layout. The first `primaryCount` cells (default 2: generally a symbol + one key amount) stay always-visible as the card's "title," marked `data-primary`; the rest get `data-label` so CSS can stack them as "Label: value" rows, hidden until "Ver más" is tapped (`row-expanded` class toggle). A row's action-column cell, which never passes through this helper, stays visible unconditionally rather than needing to be marked by hand. Group-header and total rows are excluded from the card treatment (plain table layout, since they're a subtotal/heading, not an individual record with labels to show). Action buttons are sized to a 44px touch target on mobile (WCAG 2.5.5).
- **No layout-level horizontal overflow at 375px**: fixed as part of the same pass — Instrumentos' bucket-filter row (`.segmented-toggle`) scrolls horizontally instead of forcing page width, and the Predictor page's inline `.predictor-layout` grid lost an implicit `min-width: auto` gap that let its fixed `340px` settings column push the page wider than the viewport. KPI stat grids go to a fixed 2-column layout under 860px (`.overview-grid`, `.dashboard-grid-3`) where `auto-fill` had been collapsing to a single column instead.

## Verified

- Detector (`impeccable detect`) clean on `/portfolio` at both desktop (1600px) and 390px mobile viewports — 0 primary findings, 0 advisories (pre-dates the responsive/mobile-card/bottom-nav work below; not re-run against those additions as part of this pass).
