# Design

<!-- impeccable:design-schema 1 -->

## World

Financial terminal, Operate mode. Dark charcoal surfaces by default (now with a properly-designed light counterpart, see Theming), one committed accent (cool blue) reserved for primary actions/selection/focus, gain/loss carried entirely by dedicated green/red semantics (never the accent). Two-family type system: a sans for all UI chrome, a monospace with tabular figures for every number. No emoji, no icon fonts — nav icons are hand-authored inline SVG, one consistent 1.5px stroke.

## Tokens

Defined in `webui/static/css/tokens.css`.

- Surfaces: `--bg-sidebar` (#0b0d11, darkest), `--bg-content` (#12151c), `--bg-elevated` (#1a1e27, panels/tables), `--bg-elevated-hover`.
- Borders: `--border` (hairline, 1px everywhere), `--border-strong` (inputs).
- Text: `--text-primary`, `--text-secondary`, `--text-tertiary` (#828b9c — kept light enough to clear 4.5:1 on `--bg-elevated`; do not darken without rechecking contrast).
- Accent: `--accent` / `--accent-dim` / `--accent-strong` — primary actions, active nav, focus rings only. Never used for gain/loss.
- Semantic: `--positive` / `--negative` / `--warning`, each with a `-dim` background variant for tags and banners.
- Type: `--font-sans` (IBM Plex Sans, via Google Fonts), `--font-mono` (IBM Plex Mono, tabular-nums). Scale `--step--1` through `--step-4`, fixed rem, ~1.125–1.2 ratio. Floor is 12px (0.75rem) for any label/caption text — nothing smaller ships.
- Radius: `--radius` (6px, panels), `--radius-sm` (4px, inputs/buttons).

## Components

CSS lives split by concern under `webui/static/css/` (`base.css`, `layout.css`, `components/*.css`) — one file per component family, no monolith. Loaded via plain `<link>` tags from `base.html`; no bundler.

- **Sidebar** (`components/sidebar.css`): fixed 240px, dark, active item = accent-dim background + 1px accent left border + accent icon color. Collapses to a horizontal scrollable bar under 860px.
- **Panel** (`components/panel.css`): the one container primitive — border + bg-elevated + radius. `.panel-header` for title/action row, `.panel-body` for padded content, `.panel-body.flush` (padding 0, `overflow-x: auto`) when the only child is a table. Every `.panel`'s direct child is `.panel-header`/`.panel-body`/`.panel-body.flush` — never bare content — so inset is structural, not incidental.
- **Stat strip** (`components/panel.css`): flex row of label+value pairs with hairline dividers, inside a `.panel-body.flush`. Replaces "icon+heading+text" stat cards.
- **Table** (`components/table.css`): dense, hairline row dividers, numeric columns right-aligned in mono via `.num`/`td.num`. `.table-empty` for the zero-rows state (always a sentence, never "no data").
- **Forms/buttons/status/loading/slider**: one file each, same token set. Disabled state = 0.45 opacity (accepted low contrast on disabled controls per WCAG's exemption for inactive components).
- **User menu** (`components/user-menu.css`, `shared/user-menu.js`): the sidebar-foot popover — theme toggle, an ARS⇄USD currency toggle, and a chevron that expands the four BNA rate variants (divisa/billete × compra/venta) as radios, default divisa venta. Anchored bottom-left on desktop (`bottom: 100%`); flips to open downward under 860px since the mobile sidebar has no room above it. Toggling currency fires a `currency-changed` DOM event; any view holding money values re-fetches on it rather than polling.
- **Risk gauge** (`components/risk-gauge.css`, `charts/risk-gauge.js`): one horizontal bar (0–100, bajo/medio/alto semantic coloring) reused for both the portfolio-level score on Resumen and the per-instrument score on the detail page — same component, two call sites, never a bespoke one-off. The fill is a full-width element scaled via `transform: scaleX()` with `transform-origin: left`, not an animated `width`, to keep the transition off layout-affecting properties.
- **Allocation donut** (`components/allocation-chart.css`, `charts/allocation-donut.js`): hand-built SVG arc donut (no charting library) grouping holdings by instrument type, with a color-coded legend showing each type's % of total value. Each type gets its own distinct hue (blue/amber/green/magenta/cyan/gray) — an earlier palette shaded two types in nearly the same blue, which read as "no se entiende" (indistinguishable) rather than merely suboptimal. Both the arc and its legend row are clickable (`onSelectType` callback) and apply the exact same type filter as the Tenencias chips below — the donut isn't a static illustration, it's another way to drive the one filter state. Each arc also carries a native SVG `<title>` for a zero-JS hover tooltip (label, value, %).
- **Table groups + type filter** (`components/table.css`, `portfolio/holdings.js`): Tenencias is **one** `<table>` with **one** `<thead>` — repeating a full header row per instrument type (one early version did this) reads as a pile of disconnected mini-tables, which is exactly the "tablas cruzadas" complaint that shipped this fix. Each group instead opens with a lightweight `<tr class="table-group-row" data-group="bono">` spanning all columns; every data row below it carries the same `data-group`. A row of type-filter chips ("Todos" + one per type present, built from the live holdings, never hardcoded) toggles a `type-filter-hidden` class on non-matching rows; `shared/table-filter.js`'s text search toggles its own, separate `table-row-hidden` class. Both classes independently `display: none` — a row is visible only when *neither* is present, so the two filters never fight over shared state, and `table-filter.js`'s `refreshGroupRows()` re-checks a group-row's own visibility (hidden once every row under it is hidden by either filter) after either one runs.
- **Info tooltip** (`components/info-tooltip.css`, `shared/info-tooltip.js`): a small "i" trigger that opens a click-toggled popover (same elevation language as the user menu: `bg-elevated` + border + shadow) showing the plain-language explanation a metric already has *plus* its formula substituted with the real numbers for that instance — never just the final number. One shared `initInfoTooltips()` wires every `.info-tooltip-trigger` via a single delegated document click listener, so it keeps working on rows rendered after the fact (new holdings, re-renders) with zero re-wiring. Currently used for every risk score (portfolio gauge, per-row Tenencias tag, detail page Riesgo tab) via `charts/risk-gauge.js`'s `instrumentRiskFormulaLines`/`portfolioRiskFormulaLines`, which read the intermediate numbers `portfolio/risk.py` already computes (`weight`, `volatility_score`) but didn't expose until this was built.

## Two charting libraries, each doing only what it's good at

`lightweight-charts` (TradingView's engine) owns anything that is genuinely a financial time series — candles, the forecast chart, the accuracy chart, portfolio value over time. **ApexCharts** (added via CDN, same pattern) owns every other chart — pie, radial gauge, diverging bar — after hand-rolled SVG versions of all three were tried first and rejected: no real legend, no real tooltip (the browser's native SVG `<title>`, unstyled and slow to appear), slices with no visible separation, and P&L bars that all anchored to the left regardless of sign so gains and losses looked the same shape. A charting library gives legend/tooltip/axis for free and correctly; reinventing them in raw SVG was the actual root cause of "se ve pedorro," not a detail to polish later. `charts/apex-theme.js` is the one place the dark/light palette and base chart options are defined, read by every Apex-based module (`allocation-donut.js`, `risk-gauge.js`, `pnl-bar-chart.js`, `risk-distribution-chart.js`) so none of them hardcode a second copy of the token colors.

**Chart instance lifecycle**: every Apex-based render function stores its instance on `container._chart` (not a module-level `let currentChart`) and destroys it there before re-rendering. A module-level variable silently breaks the moment the same render function is called for two different containers in the same page (it happened here: `pnl-bar-chart.js` renders both the absolute and the % charts — the second call was destroying the first's instance before it ever painted). Container-scoped storage is the only version of this that's actually correct.

The P&L bar chart is a **true diverging bar** (ApexCharts' horizontal bar naturally diverges from zero when the series has mixed signs) — gains extend right in green, losses extend left in red from a shared zero axis. An earlier version anchored every bar to the left regardless of sign, which made a -9% loss and a +9% gain look like the same shape in a different color — color alone doesn't communicate direction as fast as position does.

## Sidebar: collapsible

`shared/sidebar-collapse.js` toggles a `.collapsed` class on `#sidebar` (width `240px` → `64px`, nav labels/brand text/foot meta hidden via `display: none`, state in `localStorage`). The toggle button lives in its own full-width strip between the brand and the nav — not inside `.sidebar-brand` itself — specifically so collapsing doesn't need brand-row-specific layout logic; the button's position never moves. Hidden entirely under 860px, where the sidebar is already a horizontal bar, not a column worth collapsing. First icon tried for the toggle combined a chevron with a vertical bar meant to read as "a bracket" — at 15px it read as a stray capital "K" instead; the fix was simply using *only* the chevron.

## Why Explorador never fetches on page load anymore

`portfolio/explorer.js`'s `initExplorerView()` used to call `search()` unconditionally — meaning every single `/portfolio` page load, regardless of which tab was open, fired a live request for the *entire* BYMA universe (`GET /explorer/search?q=&limit=2000`, a real call to `data912.com`). The day data912 had a transient 502, that one fetch (15s timeout) didn't just fail the Explorador tab — it visibly starved the *other*, unrelated Resumen requests (holdings, risk, history) of the browser's small per-origin connection pool, so Resumen rendered as a wall of empty panels despite every one of those endpoints being individually healthy. The fix is the lazy pattern already used elsewhere in this app: `search()` only runs the first time `location.hash` is actually `#explorador` (checked on init and on `hashchange`), so a tab nobody is looking at never competes for a connection slot. `GET /explorer/search` also now catches its own failures and returns `{"error": ...}, 502` instead of leaking a Werkzeug debug-mode HTML traceback to an API consumer expecting JSON.

## Top bar: search, preferences, notifications

The sidebar used to end in a "Preferencias" text button that opened upward from the bottom of a 240px-tall column — once that same panel needed to work from the *top* of the page instead (moved to the header, per direct feedback referencing another app's account menu), it also stopped needing the upward-anchor/mobile-downward-override hack entirely, since a header-anchored popover only ever has room to open downward regardless of viewport size.

- **User menu** (`shared/user-menu.js`, `.user-menu-panel` anchored `top: 100%; right: 0`): currency is a `.segmented-toggle` (ARS **and** USD both always visible, the active one highlighted) — not a single button that cycles between two text states, which read as "which one am I looking at" rather than "which one is active." Theme is a real `.switch` (checkbox styled as a toggle) for the same reason. The BNA rate variant picker (4 radios behind a chevron) is unchanged, just reparented.
- **Notifications** (`shared/notifications.js`, bell icon + badge count + `.notifications-panel`): this is the same data `portfolio/alerts.js` always computed (vencimientos, dividendos cobrados, señales de venta) — `alerts.js` now only exports `computeAlerts()` (pure data, fetches holdings itself so it has no required caller args) and the rendering/open-close/badge-count logic lives in `notifications.js`, globally wired in `base.html` so it's reachable from any page, not just Resumen. Moving it out of Resumen's page flow was also what that view needed to stop feeling like a stack of unrelated panels.
- **Search**: centered in a new `.page-header-center` flex zone between the title and the action icons, widened (`max-width: 560px`) from the old corner-anchored small input. `.page-header` is three flex zones (`title | center | actions`), not a two-way `justify-content: space-between` — the center zone needs its own flex slot to actually center rather than just "whatever's left of the title."

## KPIs expand in place, never navigate away

"Hacer click y entrar en el dato" was first (wrongly) built as click-to-scroll to a different section — the actual ask was an accordion: the stat card itself grows downward to reveal its own breakdown, never taking the viewport anywhere else. Each `.stat` in the stat-strip has a sibling `.stat-detail` (`hidden` by default, toggled on click of the card): Valor Total's detail is the per-type breakdown, P&L's is a ganando/perdiendo top-3, Posiciones' is a count by type. Valor Total additionally always shows its Tenencias/Cauciones split as a permanently-visible `.stat-sub` line (not worth hiding — two numbers, always relevant) plus, once there's a reconstructed history to diff against, a day-over-day delta arrow. A fourth KPI, Cotización USD (current BNA rate for the selected variant), answers "no estás poniendo ni $ ni USD en ningún lado" directly, as does the new `shared/format.js:fmtMoney()` — every money figure in Tenencias, the stat-strip, and the detail position tab now carries an explicit `$`/`USD` prefix instead of a bare, ambiguous number.

## Historial real reconstruido (no solo desde hoy)

`portfolio/history.py:reconstruct_portfolio_value()` answers "how did my real net worth actually move" using data that was already sitting in the database and never used this way: `transactions` (what you held on any given day, by cumulative sum) × `price_history` (the real close on that day, carry-forward over gaps) = a **real** value series going back to your first transaction, not just from whenever this feature shipped. A **teórico** series runs the same calculation but substitutes Kronos's predicted close wherever `forecasts.result_json.predicted` actually covers that date, falling back to the real price everywhere else — "what would this be worth if Kronos's calls had been the ones that happened," never extrapolated beyond where a forecast genuinely exists.

Two honesty constraints that shaped the implementation:
- Most held instruments had **zero** rows in `price_history` (it only back-fills when a forecast runs against that instrument) — reconstructing against an empty series would have silently under-counted most of the portfolio. `_ensure_history()` lazily backfills any held, data912-sourced accion/cedear/bono the first time this endpoint runs (one-time network cost per instrument, cached after). Some symbols (short-term LETRAS, ON, manually-priced funds) have no historical endpoint at all — those are listed in the response's `missing_symbols` and shown verbatim under the chart, rather than being silently absent from a total that looks complete but isn't.
- `price_history` and forecast `predicted` values are already normalized "per 1 unit" at the `fetchers.py` boundary (see Multi-currency section) — this module does **not** re-divide bono/on prices by 100. It did, once, during development, and produced a total 100x too small — the exact bug this normalization boundary exists to prevent, reintroduced by a second piece of code forgetting the convention.
- No historical BNA rate is tracked day-by-day, so USD-denominated instruments in the reconstruction are converted at **today's** rate across the whole series, not the rate that applied on each past day — a declared, accepted simplification, not a precision the data can't actually back up.

## Tenencias: tabla plana, no grupos fusionados

A grouped structure (one `<tr class="table-group-row">` spanning all columns per instrument type) was tried first to add visual classification — it was the direct cause of "no se entiende, no coinciden las columnas": a merged full-width row breaks the eye's sense that every column lines up continuously, making one table read as several disconnected ones glued together. Tenencias is now one flat table with **Tipo as an ordinary, sortable column** (same `shared/sortable-table.js` used by Explorador) — classification still exists, just encoded as data in a cell instead of as a structural break in the grid. Real vertical borders between every column plus zebra-striped rows (`table.css`) complete the "como un Excel" ask; the filter chips above the table still narrow by type, they just no longer double as the thing providing visual grouping.

## Theming

Dark is the only hand-authored palette in `tokens.css`; `theme-light.css` overrides every color token under `:root[data-theme="light"]` with its own values (off-white surfaces, near-black text, deeper-saturated accent/semantic colors re-picked for contrast on white — never a CSS `invert()` or lightness flip). An inline script in `base.html`'s `<head>` applies the saved `data-theme` from `localStorage` before first paint (no flash of the wrong theme); `shared/theme.js` wires the sidebar toggle and persists the choice. `base.css` adds a 180ms background/border/color transition to body, panels, sidebar, forecast cards, and form controls — the one motion this surface earns, tied to a real state change, not decorative.

## Forecast card + candlestick chart

`portfolio/forecast-card.js` is now purely the collapsed unit — a symbol and a signal badge (comprar/mantener/vender, tag-colored) with a "Ver detalle" button — used by the dashboard's Señales grid and the Explorador's search result. It no longer expands inline: the button navigates to `#detalle/<symbol>` (see Drill-down navigation below). This is a deliberate simplification, not a feature cut — the chart/explanation rendering it used to own inline moved to `instrument-detail.js`, which is the only place that code lives now.

Charting is **lightweight-charts** (TradingView's own open-source engine, pinned implicitly to whatever `latest` resolves to — currently v5, which uses `chart.addSeries(SeriesType, options)`, not the v4 `addCandlestickSeries()`/`addLineSeries()` shorthands) rather than the Plotly already used on the original Kronos predictor page — real candles, SMA/EMA overlay, a secondary RSI pane, in the same dark/light palette as the rest of the app. Series other than the candles themselves (predicted close, SMA, EMA) set `lastValueVisible: false` / `priceLineVisible: false` — they inform through color/dash-style only, so their price-line labels don't stack on top of each other. One hard-learned rule: never call `createChart`/`addSeries` while the chart's container is still `display: none` — the container's `clientWidth` reads 0 and the chart silently renders nothing; flip visibility on *before* constructing the chart, not after.

`charts/candlestick-chart.js` also owns three small pieces that make the chart legible on its own, without a caption explaining it (`components/chart-overlay.css`):
- **Legend** (`chartLegendHtml()`): a static row of swatch+label pairs (Real/SMA 20/EMA 20/Predicho) reusing the exact colors already in `PALETTE` — never a second color definition to keep in sync.
- **Tooltip**: `chart.subscribeCrosshairMove()` drives a single absolutely-positioned div inside the chart container. It never reads values back off the series (`param.seriesData`) — instead it builds a `time -> index` lookup once from `forecast.historical`/`forecast.predicted` and indexes straight into the same arrays (`indicators.sma_20`, `ema_20`, `rsi_14`) the series were built from. That's what lets one tooltip show OHLC *and* SMA/EMA *and* RSI together even though RSI lives in a visually separate pane rendered by a second, unrelated `createChart` call.
- **Range shortcuts** (`rangeControlsHtml()` + `wireRangeControls()`): 1M/3M/6M/1A/Todo buttons that call `chart.timeScale().setVisibleRange(...)` against data already in memory — never a new fetch. Every preset anchors its right edge to the *last predicted point*, not "today," so the forecast cone is always in view; only how far back history starts changes.

## Drill-down navigation

Resumen, Instrumentos, Transacciones, Señales, and Explorador all go "from less to more": a collapsed row/card shows just a symbol, a type, and a signal, and every one of them links to `#detalle/<symbol>` for the full picture — one dedicated full-width page within the workspace, never an expansion inside a grid cell (a 3-up grid expanding one cell used to push its neighbors around). `portfolio/tabs.js` recognizes the `detalle/` hash prefix as a dynamic route distinct from the fixed view list and hands off to `portfolio/instrument-detail.js`, which renders into `#instrument-detail-root`. Its one "Volver" action is a plain `<a href="#resumen">` **breadcrumb above the panel** (`.detail-breadcrumb`), not a lone button sitting by itself inside its own `.panel-header` strip — a bare button in an otherwise-empty toolbar read as "en un lugar rarísimo" once it was the only thing on the page with nothing to anchor it. A real `<a>` also means middle-click/keyboard/right-click-to-copy all work for free, which a `click` handler on a `<button>` didn't give.

The detail page itself has a **local tab bar** (`components/detail-tabs.css`) — Pronóstico / Posición / Riesgo / Precisión — instead of stacking all of it in one long column (an earlier version did exactly that and read as "una aglomeración de información" once Posición and Riesgo were added alongside the chart). Posición and Riesgo only appear as tabs when the symbol is an actual holding with that data; Precisión appears whenever the symbol has a local `instrument_id` (held or not — any instrument added via Instrumentos accumulates its own forecast history). A symbol opened from Explorador with no local row at all gets just the one Pronóstico tab, and the bar itself doesn't render when there's nothing to switch between (`tabsBarHtml()` returns `''` for a single-tab list). Tab state is local DOM state (an `active` class + `hidden` attribute), never a second hash segment — `#detalle/GGAL/riesgo` would be over-engineering for a UI concern that never needs to be linkable on its own.

One gotcha the Precisión tab re-triggered: its chart must **not** be constructed eagerly alongside Pronóstico/Posición/Riesgo, because it isn't the default-active tab — its container is still `hidden` (same effect as `display: none`) at render time, so `createChart` would read a 0 width and draw nothing (the exact failure mode already called out below for the Pronóstico chart, just reached through a different hidden mechanism). Fix: `loadAccuracy()` only runs the first time the Precisión tab button is clicked, not on initial page render.

## Market browser (Explorador BYMA)

Lists the full BYMA universe (~1300 instruments) by default — it used to render nothing until the user typed a query, which is the opposite of what a world-class screener (TradingView, Yahoo Finance) does: show the data, let search/filter *narrow* it, never gate it. `portfolio/byma_universe.search()` already supported an empty query (it's just "no symbol filter"); the only change needed was the frontend no longer short-circuiting on an empty `#explorer-search` and requesting a high `limit` (2000, covers the whole universe) instead of the old default of 20. It's a real `<table>` now (sortable columns via a click handler on `th.sortable`, `.table-link` rows into the same `#detalle/<symbol>` drill-down as everywhere else), not a column of button-rows.

Rendering ~1300 rows as one page would make the whole document 50,000+ px tall (confirmed the hard way) — `.table-scroll` (`max-height: 70vh; overflow-y: auto`) caps it to one bounded, internally-scrolling panel with a sticky `thead`, while the search/type-filter row stays outside that scroll container so it's always visible. Any other table that grows unbounded over time (Transacciones' Historial, eventually) can reuse the same class.

## Resumen: drill-down + genuinely informative (not just a snapshot)

Every number on Resumen used to be inert — a stat, a gauge, a table, with nothing behind it. Two complaints in the same breath ("dejame hacer click y entrar en cada dato" and, separately, "no me dice mucho") turned into one redesign, because they're two sides of the same problem: a dashboard that only shows the current totals, with no path to *why* and no path to *more*.

- **Stat-strip is clickable** (`portfolio/holdings.js`'s `wireStatClicks`): Valor Total always shows its Tenencias/Cauciones breakdown as a second line (no click needed — that one's cheap enough to just show), P&L click sorts Tenencias by P&L descending and scrolls to it, Posiciones click resets the type filter and scrolls. None of these needed a new endpoint — the data was already in hand, just not wired to anything.
- **Tenencias is sortable** (`shared/sortable-table.js`, shared with Explorador's own column sort): sorting happens *within* each type group, never flattening the table — the grouping is structural, not decoration, so a sort has to respect it.
- **Riesgo de cartera shows its own breakdown directly**, not behind another click: "Mayores contribuyentes al riesgo" (top 3 by `valor_actual × risk.score`) sits right under the gauge's explanation.
- **Historial de cartera** (`portfolio_snapshots` table, written once per day inside `POST /refresh-quotes`, always in ARS regardless of the display-currency toggle so the line never jumps for the wrong reason): a real line chart of value over time. Brand-new portfolios show an honest "come back tomorrow" instead of a one-point chart pretending to be a trend.
- **Resumen narrativo** (`holdings.js`'s `buildNarrative`): one sentence synthesizing what's already fetched — today's biggest mover, the riskiest holding, and (only once 2+ snapshots exist) the value trend since the last one. Never invents a trend it can't measure yet.
- **Alertas** (`portfolio/alerts.js`): plazos fijos/cauciones vencidos o a vencer en ≤7 días, dividendos cobrados en los últimos 7 días, holdings con señal de venta — all assembled client-side from endpoints that already existed, zero new backend. An honest empty state ("Nada necesita tu atención ahora") when there's genuinely nothing, which is the common case for cauciones here since they're all historical/already-settled import data, not live open positions.
- **P&L por instrumento** (`charts/pnl-bar-chart.js`): a second chart next to the allocation donut — ranked horizontal bars, red/green, click-to-drill into the instrument. Answers "who's making or losing me money," which the donut ("where is my money") never could on its own.

## Multi-currency (ARS/USD)

Every instrument has a native `currency` (ARS or USD); the user picks a `display_currency` and a BNA rate variant in the user menu, and `/api/portfolio/holdings` converts every money field server-side using the live rate scraped from `bna.com.ar/Personas` (`portfolio/fetchers.py:fetch_bna_rates`, 5-minute in-memory cache — BNA has no public API). `pnl_pct` is never converted, since it's a ratio, not a monetary amount. Conversion lives in `routes.py`, not `db.py`, specifically to avoid a circular import (`db.py` is imported by `fetchers.py`, which is where the rate lookup lives).

## Forecast accuracy (predicted vs. actual)

`portfolio/accuracy.py` answers "how good were Kronos's past calls, really" using data that already exists — every past `forecasts.result_json` (its `predicted` array) crossed against `price_history` once those same dates have a real, known close. No new table, no background job: it's a pure function over two already-queried row sets (`compute_accuracy(forecasts, price_history)`), exposed at `GET /instruments/<id>/accuracy`. Matching is by **date** (`YYYY-MM-DD`), not exact UNIX timestamp — `forecasts` stores predicted points as UTC seconds while `price_history` stores an ISO string, and the two are built through slightly different paths; comparing by calendar date sidesteps any timezone-of-day drift between them without losing precision that matters (nothing here is intraday). Directional accuracy counts only each forecast's *first* predicted step against its own last known historical close — the only comparison that is unambiguous regardless of how far out the rest of that run's horizon goes. If no past forecast has any predicted date old enough to already have a real price, the endpoint returns `null` and the UI shows an explicit "not enough time has passed yet" sentence — never a fabricated 0% or empty chart presented as a real answer.

- **Nav as data, not markup**: `webui/nav.py`'s `NAV_ITEMS` is the only place sidebar entries are listed; `base.html` loops over it, `_icons.html` maps each `icon` key to its SVG. Adding a page means editing one Python list, not every template.
- **Client-side tabs on `/portfolio`**: Resumen/Instrumentos/Transacciones/Plazos Fijos are one route, switched via `location.hash` (`static/js/portfolio/tabs.js`); `static/js/shared/nav.js` marks the matching sidebar link active by comparing `pathname + hash` against each link's `href` — no per-page active-state logic duplicated. `tabs.js` also recognizes the dynamic `detalle/<symbol>` hash (see Drill-down navigation) without adding it to the fixed view list or to `nav.js`'s matching — there is intentionally no sidebar item that's ever "active" while on a detail page.
- **One search box, whatever table is showing** (`shared/table-filter.js`): a single `#workspace-search` input, centered and widened in the header's `.page-header-center` zone, filters `tbody tr` inside the currently-active `.view` by plain text match, re-applied on `hashchange` so switching tabs keeps the query live. It just hides non-matching rows via the shared `.table-row-hidden` class — Tenencias being a flat table now (see below) means there's no group-row visibility to reconcile afterward either. Explorador keeps its own `#explorer-search`, which queries the full BYMA universe via the API — a different search over a different, much larger set of instruments than "what I already hold."
- **Date-range filter** (`shared/date-range-filter.js`): two bare `type="date"` inputs next to a table's panel title (Transacciones' Historial + Dividendos y Rentas share one), comparing each row's first-cell date string directly — ISO `YYYY-MM-DD` sorts lexicographically the same as chronologically, so there's no `Date` parsing to get wrong. Same independent-class pattern as the type filter: `date-filter-hidden` is its own class, never touching `table-row-hidden`.
- **JS is ES modules, one file per concern** (`static/js/<page>/<feature>.js`), each exporting an `init*View()` that wires its own listeners; a thin `main.js` per page just calls them. No inline `<script>` blocks, no shared mutable globals beyond the explicit `state.js` object on the Kronos page.
- **Numbers**: always render through `shared/format.js`'s `fmt`/`fmtPct` and always tag the cell with `.num` — this is what keeps every price/quantity/percentage on the tabular-mono grid.
- **Empty/neutral states carry no false color**: a zero/empty P&L or stat is neutral text, not green — color only appears once there is a real positive/negative value (see `portfolio/holdings.js`'s `renderStatStrip`).

## Verified

- Detector (`impeccable detect`) clean on `/portfolio` at both desktop (1600px) and 390px mobile viewports — 0 primary findings, 0 advisories.
- `.info-tooltip-panel` toggles via `display: none` / `display: block` on `:hover`/`:focus-within` (pure CSS, no JS open/close state), not `opacity`/`visibility` — tried that first, and it broke two things at once: `visibility: hidden` still reserves full layout space, so ~20 invisible 260px popovers anchored inside already-narrow panels were silently widening the page's scrollable area past the viewport on mobile; and the detector's `content-hidden-at-rest` check flagged the same always-present-but-invisible text as the AI-generated "content shipped but never becomes visible" anti-pattern it's built to catch. `display: none` removes both problems at the root. Switched away from click-to-toggle to begin with because that read as confusing — "el tooltip debe estar al pasar el mouse."
- Notifications badge: white text on `--negative` (#ef5b5b) measured 3.3:1, short of WCAG AA's 4.5:1 for small text. The badge uses its own darker red (`#c0392b`) instead of reusing the semantic negative token — a filled badge with small white text is a different contrast scenario than `--negative` used as text-on-dark (its normal usage), and needed its own color rather than bending the shared token.
- `/` (Kronos predictor) has two accepted, reviewed findings predating this work: the settings-column/preview-column height mismatch (Operate mode, not a Persuade fold) and the disabled primary button's low contrast (WCAG exempts inactive controls). Two regressions caught and fixed on the way: `.page-header-title { flex-shrink: 0 }` prevented the title/subtitle from wrapping on mobile, overflowing the header row — removed, since nothing actually required it not to shrink; and the two `currentChart` singleton bugs described above.
